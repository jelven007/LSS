## 2. 版本标识规则

主应用采用语义化版本 `MAJOR.MINOR.PATCH`。发布前由维护者同步根项目、前后端包、
`VERSION`、CHANGELOG、发布文档和镜像标签；CI 只验证一致性，不在主线推送后自动生成
额外版本提交。生产清单必须在 Tag 之外固定镜像 digest。

一次可复现交付必须同时记录：

1. 应用语义版本，以交付提交中的 `VERSION` 为准。
2. 完整 Git commit SHA。
3. 部署环境和 schema 版本。
4. 镜像 digest 或桌面产物 SHA-256。
5. 对应测试、发布和恢复证据。

历史同号不同提交不能作为新的发布规则。应用版本由维护者同步，CI 校验一致性。
Git Tag、稳定制品和生产状态分别核验；部署、缺陷与验收记录同时保存完整 commit SHA
和镜像 digest，不把标签存在当作生产可用证明。

`06d4e0b` 和 `b360d77` 的功能修复更新曾未同步递增应用版本，仍写作 `0.4.0`。
随后以 `0.4.1` 补齐版本，并取消校验脚本和开发规则中的“版本不变”例外；
此为历史版本管理记录，不追溯改写。当前 `.github/workflows/product.yml` 只验证
各包版本一致，不自动递增版本或创建标签；版本和标签由发布负责人显式更新。

## 3. 分支与发布归类

- `main`：唯一集成主线，必须包含已经决定保留的最新代码和文档。
- 功能分支：只承载尚未归并的工作；归并后不再作为“最新版”引用。
- `v*` Git 标签：主线质量门通过后由发布负责人创建的不可变源码版本点；同名冲突不覆盖。
- 稳定 Release：对应标签的目标产物完成验收后发布，不由自动源码标签推断。
- 生产版本：以实际部署提交和镜像 digest 为准，不自动等同 `main` 或最新标签。
- 历史报告：记录当时事实，不追溯改写成当前状态；文档顶部的当前状态应链接本文。

多人协作的分支基线、主线并发、回滚、镜像指针和远程权限见
[多人协作与版本管理](./collaborative-versioning.md)。远程已启用 main 禁止删除和
非快进、`v*` 标签禁止更新和删除；个人仓库拒绝内置 Actions App bypass，
完整 PR/复审/质量强制规则仍需专用 GitHub App，不能从模板存在推断已启用。

## 5. 更新要求

应用版本字段由发布提交统一更新，CI 负责拒绝不一致版本。以下状态变化必须同步本文件：

- `main` 归并新的版本候选；
- 应用语义版本或稳定标签变化；
- 生产部署、回滚或 schema 迁移；
- 二期步骤由“本地通过”转为“候选通过”或“生产签收”；
- 应用更新源变化。
